- (direction) shoe-tracker: mobile web app to log shoe sightings on autobahn with timestamp and GPS
- (requirement) R1: One-tap button on mobile web interface records shoe spotting with current timestamp and device geolocation
- (requirement) R2: First-time prompt asks for user name and associates it with all subsequent log entries
- (requirement) R3: Interface allows user to view and update their name at any time
- (requirement) R4: List view displays all recorded shoe sightings with timestamp, location coordinates, and name
- (requirement) R5: Map view displays interactive geographical markers for all recorded shoe sightings
- (requirement) R6: Backend exposes lean REST API for recording sightings, querying sightings, and user identity
- (constraint) C1: Two-tier architecture with frontend separated from backend and shielded by a lean API
- (constraint) C2: Backend implemented in Kotlin using Quarkus framework
- (constraint) C3: Persistence in SQLite database
- (constraint) C4: Packaged and hosted as a single container serving both Quarkus backend and frontend assets
- (constraint) C5: Mobile-first responsive UI optimized for quick single-tap action
- (assumption) Map uses OpenStreetMap with Leaflet.js to avoid API key requirements
- (assumption) User name is stored in browser localStorage with client ID for lightweight session identity
- (assumption) Browser Geolocation API is used to acquire latitude and longitude coordinates
- (question) Offline support: Should sightings queue locally in browser storage when driving through dead zones and auto-sync?
- (question) User scoping: Should the map and list show only 'my shoes' (current user) or all shoes recorded in the system?
- (event) Pass 1 Coherence: validated against Spec Law rules 1-6 and 8
- (event) Pass 2 Preservation: validated all source claims captured in ticket
- (decision) Offline support deferred from MVP; direct online API submission only
- (decision) Views show all users' shoes with visual differentiation (distinct color for own shoes) and a filter toggle to hide other users' shoes
- (requirement) R4: List view displays recorded shoe sightings with timestamp, location coordinates, and recorder name, with distinct visual indicator for user's own shoes and a toggle to hide other users' shoes
- (requirement) R5: Map view displays interactive markers for recorded shoe sightings, using distinct marker color for user's own shoes and an option to toggle visibility of other users' shoes
- (event) Self-validate: Coherence and Preservation passes verified updated R4, R5, and decisions
- (decision) Geolocation: continuously watch position in background via watchPosition so GPS is hot and instantaneous upon tap
- (decision) Accidental taps: enforce mandatory cooldown period after each recorded tap to prevent duplicates
- (decision) Identity: author name is an immutable snapshot on each sighting at capture time; future changes do not rewrite history; collisions ignored
- (decision) Bearing: ignore compass heading for MVP; parked as future enhancement
- (decision) LDAP: dedicated login via LDAP parked as future backlog idea
- (decision) Lifecycle: shoe sightings remain on the map indefinitely with no TTL
- (decision) Safety: no confirmation or disclaimer dialog on launch
- (requirement) R1: One-tap button on mobile web interface records shoe spotting with current timestamp and hot device geolocation coordinates
- (requirement) R7: Interface enforces a mandatory cooldown period after logging a sighting to prevent accidental duplicate taps

- (decision) Shoe metadata: shoe types and colors deferred as future backlog idea
- (decision) Identity for MVP: user_id and user_name are the same string (the entered name). Dedicated login, profile management, and changing username deferred to backlog.
